# design
- Preserve existing visual design and styling when making content updates — avoid full UI rewrites unless explicitly requested. Prefer targeted content changes (text, badges, copy) over complete redesigns. Confidence: 0.70
- When adding new content cards to a dashboard, place them side-by-side in the existing grid row rather than in a separate full-width section below — full-width stacked sections push content below the fold and require scrolling to see. Confidence: 0.65
- Do not expose internal tech stack details (Judge0, Monaco Editor, specific engines/libraries) on public-facing pages like About or Landing — the user considers these implementation secrets. Confidence: 0.85
- In the competition code editor, the description panel must be **draggable/resizable** — not just collapsible with a toggle button. Users should be able to drag a divider to adjust panel sizes to their preference. A fixed 50/50 split or a simple collapse toggle wastes room while coding; the editor must be flexibly adjustable by the user. The DSA sheet layout is the canonical reference for this pattern. Confidence: 0.95
- The standalone student code editor (CodeEditor.jsx) should also have **draggable/resizable panels** — users should be able to adjust the editor height and input/output panel sizes from all sides via a draggable divider, not just a fixed layout. Confidence: 0.9
- When hiding a feature like leaderboard, show a placeholder message (e.g., "Leaderboard will be displayed soon") instead of removing the tab/UI element entirely — students panic if the tab disappears. Confidence: 0.70
- Database fields should represent a single atomic concept — never encode two distinct pieces of information into one column (e.g., "TE-A" storing both class year AND division). Compound values cause filtering, grouping, and display bugs because no single query can cleanly separate them. Each independent attribute deserves its own column. Confidence: 0.80
- Division is an organizational label, not a visibility/access-control filter. When notes are uploaded for a specific division (e.g., BE-B), ALL students of that class year (all BE divisions) should see them — the division field helps label and organize notes within the year group but should never be used to restrict which students can access them. Confidence: 0.55
- Default visibility should be scoped to the student's own division (e.g., a BE-A student sees only BE-A notes by default), but students must have the ability to browse/view notes from other divisions within their class year if they choose — the pattern is "scoped by default, expandable on demand." The division field should act as a default filter, not a hard access gate. Confidence: 0.65
- When applying a visual theme/color-palette refresh to a parent component, also update ALL child/sub-components (sidebars, description panels, lists) to match the new palette — partial updates leave old-colored sub-components dominating the visual impression, and users will report "nothing changed" even though the parent was updated. Visual consistency requires the full component tree to be refreshed at once, not piecemeal. Confidence: 0.75
- For drag-to-resize panels inside flex containers, use pixel-based widths (derived from `getBoundingClientRect()` + mouse position) rather than percentage-based widths — percentage values interact unreliably with flex layout calculations, causing jumpy or unresponsive drag behavior. Pixel math with `flexShrink: 0` on the resizable panel is the reliable pattern. Confidence: 0.85
- For split-pane/resizable layouts, use a strict 3-element architecture: `[Left Panel — controlled width, shrink-0] | [Resize Handle — shrink-0, fixed 4–6px] | [Right Panel — flex:1, min-w-0]`. The parent must be `display: flex` with `overflow: hidden` and `height: 100%`. Both flex children need `min-width: 0` (or `min-w-0` in Tailwind) to override the default `min-width: auto` — without it, flex items refuse to shrink below their content size and the drag divider fights CSS instead of controlling layout. The right panel uses `flex: 1` to consume remaining space; it must never have a fixed width, `100vw`, or any hardcoded dimension that competes with the split-pane logic. Confidence: 0.90
- When resizing a container that holds a Monaco editor, call `editor.layout()` on every frame during the drag (via `requestAnimationFrame` throttling) AND on drag-end — Monaco caches its container dimensions and won't reflow unless explicitly told. Without this call the editor appears to resize correctly but its internal layout (line numbers, minimap, cursor position) stays at the old size. The split-pane controls layout, not Monaco — the editor must be a passive consumer of container dimensions. Confidence: 0.90
- When manually calling `editor.layout()` on Monaco during drag/resize, disable `automaticLayout` (set it to `false`) — Monaco's internal ResizeObserver fights manual DOM width writes. Having both active causes jittery or unresponsive drag behavior because Monaco's auto-layout races against the manual `layout()` calls. Confidence: 0.80
- For drag-to-resize panels where React state updates cause lag, use direct DOM manipulation (`el.style.width = w + 'px'`) during the drag via ref, syncing to React state only on mouse-up — bypassing React's async batched re-renders gives instant visual response. The pattern is: write to DOM directly on every mousemove (zero render overhead), then call `setState` once on mouse-up for React to catch up. Confidence: 0.75
- User-generated text rendered in the UI (e.g., evaluator comments/remarks in competition results) must preserve the original formatting — line breaks, multiple spaces, emojis, and **bold**/*italic* markup — render it with a `<pre>`-style container (`whitespace-pre-wrap break-words`, inherited font) rather than a plain `<p>`, which collapses whitespace and strips emphasis. The user explicitly asked for comments to "not be stripped" and for spaces/emojis/bold to be supported properly. Confidence: 0.80
- Leaderboards shown to students should prominently highlight the student's own entry — a highlighted row (e.g., colored ring + "You" badge) plus a summary strip at the top showing their rank and score — so students can instantly see where they stand without scanning the list. Rank and position ("39 / 136") are the same information; show the total inline with the rank (e.g., "39 / 136") rather than a separate "Position" box, which the user flagged as redundant. Confidence: 0.75
- Avoid displaying redundant/duplicate information in the UI: if two displayed values convey the same fact (e.g., "Your Rank: 39" vs. a separate "Your Position: 39 / 136" card), show one, not both — the user explicitly called this out and asked for the duplicate removed from the frontend. Confidence: 0.70
- When a view contains the user's own entry or a flagged item buried in a long list (e.g., the student's row in a large leaderboard, or a problem with a new evaluator review), auto-scroll (smooth) to that item when the view opens — don't make the student hunt or scan to find it. The user explicitly asked whether the screen could auto-scroll to their rank in the leaderboard and to the problems that received reviews. Confidence: 0.70
- User-facing notifications for new content (e.g., evaluator reviews) should track read/acknowledged state per item and disappear only after the user explicitly acknowledges each one — e.g., an unacknowledged-count banner at the top plus per-item badges that clear once all are acknowledged. The user asked that the "new review" notification go away once the student reads and acknowledges it. Confidence: 0.70
- Notification banners should name the exact items affected (problem numbers and/or titles, e.g., "Review on Problem 2 (Two Sum)"), not just a generic "you have N reviews" — the user asked the banner to mention which question each review is for so students can find it easily without hunting. Confidence: 0.70
- When the user asks to make a page's frontend "best possible" in UI and UX (e.g., competition results with My Results + Leaderboard, the competitions list page, and the student main dashboard), deliver a comprehensive high-polish redesign across the whole flow — gradient hero headers, skeleton loaders, richer cards with hover states, contextual empty states, search/filter on tables, podium-style top-3 displays — with full mobile responsiveness on every screen, not incremental tweaks to a single component. The user repeatedly asks for this ("best possible frontend in UI and UX", "all mobile friendly UI proper responsive", "proper best professional") and expects sibling pages in the same flow (list page + detail page) to be improved together; the student dashboard polish should include time-aware greetings, section labels, expanded quick actions, and a footer. Confidence: 0.75
- When a full UI redesign IS explicitly requested, change only the visuals and preserve every piece of existing working logic — registration flows, filters, action buttons, read-only toasts, preload-on-hover, empty states. Audit the redesigned component against the original and revert any accidental behavior changes (e.g., replacing a time-remaining display with a different field). The user explicitly instructed to "keep every piece of working logic intact and only change visuals." Confidence: 0.75
- Dense technical content in student-facing result views (full problem description, examples, constraints, per-test-case pass/fail) should be hidden behind a collapsible panel that defaults to collapsed — students who don't want details see a clean, uncluttered summary (score, code, review) and only those who want them expand. Long lists should preview a few items with a "Show all" affordance so the expanded view never looks messy. The user explicitly asked for this opt-in design: "it should not be messed if some students dont want to see... but if they have mood to see those details can see properly." Confidence: 0.80
- For code submission results, students should be able to see exactly which test cases passed and failed — input, expected output vs. actual output, and error/status per test case — not just a score or a tests-passed count. The user wants students to get a clear idea of precisely where they lost marks ("exact which test cases where passed fails ok so they get breif idea"). This requires the backend to expose the stored per-test-case results even when the frontend shows them behind an expander. Confidence: 0.65
- Problem/question statements should be written in a short, direct, plain style — not long, story-flavored narrative framing. The user flagged questions written "in a story way" as "long and twisted" and wants them rewritten to be direct (e.g., "Find Minimum and Maximum" instead of "The Scoreboard Summary"), keeping the logic, function names, and test cases unchanged while only simplifying the description text (and titles if desired). Confidence: 0.70
- AI assistants/chatbots built for students should have a cute, friendly persona — a memorable cute name (e.g., "Nexi"), warm encouraging tone with light emoji use, and an "online 24/7" presence — and must answer in a clean, properly formatted structure (short paragraphs, bullet lists, bolded key numbers) rather than walls of text. The user explicitly asked for "a cute chatbot with cute name" that "properly answers in proper format." Confidence: 0.65
- AI-powered actions that touch a student's own work (e.g., reviewing code against test cases) must present options first and require explicit confirmation from the student before executing — "every doubt can [be] handle[d] by properly confirming from the students side." Similarly, escalation to a human admin should be offered and confirmed by the student rather than auto-fired, unless the query is clearly critical. Confidence: 0.70
- AI chatbot answers should be token-conscious: simple queries (greetings, yes/no, status checks) get a 1-2 sentence answer, and longer detail is reserved for queries that genuinely need it (score breakdowns, code reviews, step-by-step explanations). The user framed this explicitly as cost/abuse control: "small answer for simple queries... this is to save the tokens and abuse usage." Confidence: 0.85
- Chatbot ticket creation should be one-step and frictionless: the student just states the issue, the AI immediately generates the subject + description itself, and the student only gets a single "Shall I send it?" confirmation — no clarifying questions, no multi-step back-and-forth. Confidence: 0.85
- After the AI performs an action for the student (e.g., creating a ticket), confirm with a friendly message stating what happened and what's next — e.g., "Your ticket has been sent to the Coding Nexus Team — someone will reply soon, keep an eye on your email." The user specified the exact confirmation copy they want shown after sending. Confidence: 0.75
- Chatbot should support topic switching mid-conversation: when the student changes topic, follow the new topic immediately (don't keep answering the old one or ask if they're done), and offer a "new topic / clear conversation" control in the chat header that resets context in one tap. Confidence: 0.70
- Chatbot memory should be session-scoped short-term memory: keep the last ~12 turns as multi-turn context so follow-ups referencing earlier topics work ("what about my rank?"), but never persist long-term (privacy + token cost), and never derive live facts (scores, ranks) from memory — always from the real DB data. Confidence: 0.65
- AI chatbot responses should stream progressively so users see responses immediately, but the stream must not break final JSON parsing: stream raw text deltas as newline-delimited JSON and treat the server-parsed final payload as the source of truth that replaces the streamed text. The user explicitly asked to "use streaming so users see responses immediately" and to implement it "without breaking JSON/final-response parsing." Confidence: 0.75
- Do not send unnecessary DB/student data to the model — trim the student-context JSON and history to only what the task needs, with caps on prompt size and history turns/chars, so the request fits the model's context window and minimizes data exposure. The user explicitly said to "not send unnecessary DB/student data to the model." Confidence: 0.75
