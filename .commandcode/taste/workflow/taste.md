# workflow
- Expects a self-contained local development environment: a single `docker compose up` should bring up ALL required services (app, database, Judge0, Redis, etc.) locally without depending on any external services running elsewhere. Local dev must be truly independent — the user wants to develop features on localhost, test everything, then push to production with confidence. Confidence: 0.70
- Before committing and pushing code on behalf of the user from a shared or multi-user machine, verify that git identity (name + email) matches the user's GitHub account — don't assume the machine's local git config belongs to the user. The user explicitly wants commits attributed to their own username. Confidence: 0.65
- Before pushing to the main branch from a production server, perform a thorough pre-push audit: (1) check git status and diff to understand what's being committed, (2) grep the diff for any accidental secrets (API keys, tokens) using known secret patterns, (3) confirm that gitignored files like `.env.docker` are NOT tracked. The user explicitly asked to "properly check and then commit push" — they expect a safety net against leaking secrets or pushing unintended files. Confidence: 0.70
- Code in the student code editor should persist in **localStorage** so that when a student navigates to another feature of the site and returns, their code is still there. This applies to the standalone `/student/code-editor` route. Confidence: 0.9
- When switching languages in the code editor, code and input should persist per-language — only the output should be cleared. Each language slot should independently remember its code; switching to a previously-used language restores that language's saved code, while switching to a new language for the first time shows a fresh template. Language switch is a syntax change, not a reset of user content. Confidence: 0.95
- For production or infrastructure changes, first inspect the current state, then present a clear plan of what will happen, and wait for explicit confirmation ("yes") before executing. Confidence: 0.80
- For feature implementation requests, skip planning/discussion and implement directly and quickly; explain what was done after implementation, not before. Confidence: 0.70
- When backend changes involve DB schema modifications or new API routes, proactively run the migration and rebuild/restart the server (Docker/PM2) — don't declare the task done until the deployed server picks up the changes. Confidence: 0.80
- Frontend-only changes require `npm run build` to deploy; backend changes require Docker container rebuild and `docker compose up -d` to restart. Don't mix up the deployment paths. Confidence: 0.70
- When changes span both frontend AND backend (new routes, new pages, new API endpoints), run BOTH the frontend build (`npm run build`) AND the Docker rebuild (`docker compose up -d --build`) — the system won't work in production unless both deployment paths are completed. Confidence: 0.75
- When improving layout or editor components, reference the DSA sheet as a pattern for how the editor should behave — it serves as the canonical example of a well-structured, flexible editor layout. Confidence: 0.85
- When the user asks for a way to reconfirm system health or monitor critical services on an ongoing basis, provide a reusable script (e.g., `healthcheck.sh`) rather than a one-off command — the user wants a single command they can run anytime to verify everything at once, not a list of ad-hoc checks to remember. Confidence: 0.85
- When the user requests CI/CD or automation infrastructure, they expect a comprehensive, zero-mistake deliverable: all workflow/config files, a step-by-step setup guide enumerating every manual action required (GitHub secrets, SSH keys), and clear demarcation of what's one-time setup vs. ongoing automation. The user explicitly asked for a "complete .md file" and "step by step" and "without making any single mistake." Confidence: 0.80
- When replacing outdated or broken configurations/documentation with new versions, explicitly delete the superseded files rather than leaving them alongside the new ones — the user values a clean repo where only active, working files exist and there's no ambiguity about which file to use. Confidence: 0.70
- For DevOps/infrastructure documentation, produce two complementary artifacts: a step-by-step setup guide (actionable, for first-time setup — e.g., SETUP_CI_CD.md) and an architecture reference document (explanatory, for understanding how the system fits together — e.g., ARCHITECTURE.md). Setup guides and architecture references serve different audiences and the user approved both being created. Confidence: 0.70
- When the user explicitly says "don't push until I say" or "don't push yet," respect that instruction — make the fixes, stage them, but wait for explicit permission before committing and pushing. The user sometimes wants to review changes before they go live. Confidence: 0.85
