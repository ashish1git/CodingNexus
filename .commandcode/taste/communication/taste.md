# communication
- Explicitly report or enumerate every change made when performing edits — the user wants to be told what was changed, not just have it done silently. Confidence: 0.70
- When applying system-level fixes (infrastructure, config, env), present a structured before/after comparison — ideally as a table showing each issue's state before the fix vs. after. The user wants to see "what was before and now" for every change, not just a summary of what was done. Confidence: 0.80
- When documenting CLI commands: show the simplest, no-argument command first as the primary example, then mention optional arguments separately. Don't list all variants at once — the user finds multi-variant command references confusing. Confidence: 0.75
- When the user asks multiple specific questions (especially in a troubleshooting context), address each one individually with a dedicated section or header — don't merge answers or skip any question. The user notices when questions go unanswered and explicitly repeats them if skipped. Confidence: 0.85
- When explaining complex technical failures or root causes, use plain, simple language and avoid unnecessary jargon — the user explicitly prefers explanations in "very simple way." Confidence: 0.85
- When the user asks a conceptual "what does X do / why does X exist" question (e.g., "whats the use for dockerfile," "why docker compose"), provide an educational explanation with a simple analogy before the technical answer — the user wants to understand the fundamentals, not just get a fix applied. Confidence: 0.85
- When the user asks for a recap of what was changed or fixed across a debugging session, present it as a numbered sequential step-by-step walkthrough in chronological order — the user explicitly asks for things "sequentially" and wants to see the progression of each fix, not a merged summary. Confidence: 0.75
- When the user asks about changes the assistant made (especially to docs or config), explain both WHAT changed and WHY it was changed — the user explicitly asks for the reasoning behind edits, not just a list of what was modified. Confidence: 0.70
- When the user pushes back on a claim with their own intuition or experience (e.g., "I think X is actually slower"), or reports a feature is broken based on what they observe (e.g., "i think is tjis not workin"), verify empirically rather than re-stating the original claim or dismissing it — run benchmarks, time the operation, check the actual code/data path, and present real evidence. If the evidence proves the user right, acknowledge it honestly rather than deflecting. Confidence: 0.70
- When the user pastes a large CI/CD log dump and asks for deep analysis ("analyse this properly deeply each line and tell"), provide a structured categorized breakdown — group issues by type with counts, severity levels, and clearly distinguish between functionally-impactful errors vs. cosmetic lint noise. Don't summarize or skip categories. Confidence: 0.70
- When the user reports a bug and says "fix fast and tell me why it happens", deliver both in the same pass: apply the fix quickly AND explain the root cause of why the bug occurred — the user wants the underlying reason explained (e.g., why emails came from both keys, why the counter showed 0/1), not just a list of changes made. Confidence: 0.70
