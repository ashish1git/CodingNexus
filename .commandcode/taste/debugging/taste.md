# debugging
- When a display issue like "N/A" or garbled values appears on the frontend, verify the raw database data (not just the API response or frontend code) — the root cause may be corrupt/malformed stored data that no amount of frontend or API code changes will fix. A `SELECT` query on the actual table is the fastest way to rule out (or confirm) a data integrity problem. Confidence: 0.85
- When diagnosing service failures (especially nginx/proxy), first identify which instance is actually serving production traffic — there may be duplicate instances (e.g., system-installed via apt vs Docker container) and the one you're debugging may be irrelevant. Don't assume the Docker container is the active one; check `ss -tlnp` to see which process owns the port. Confidence: 0.75
- When multiple systems fail simultaneously (email, editor, APIs, etc.), perform exhaustive, wide-scope analysis — check all containers, logs, nginx, backend services, environment variables, and API keys before narrowing to a single cause. The user expects root-cause identification, not piecemeal symptom fixes. Confidence: 0.75
- When investigating systemic failures, trace the timeline to identify when things last worked — the user wants to understand how the problem was introduced (e.g., which merge, deployment, or config change triggered it), not just a snapshot of what's currently broken. Confidence: 0.70
- When debugging a project on a shared server, explicitly check whether other projects or containers on the same machine could be interfering — the user considers cross-project misconfiguration a real risk and wants it ruled out. Confidence: 0.65
- After diagnosing failures, explicitly confirm that all issues are recoverable — the user wants reassurance that no permanent damage has occurred before fixes are applied. Confidence: 0.80
- When the user asks "how" something broke (not just "when" or "what"), trace the full causal mechanism — explain the technical interaction that caused the failure (e.g., Docker Compose env resolution priority, shell pollution overriding .env), not just which config file changed. The user wants to understand the "physics" of the failure chain. Confidence: 0.70
- When fixing infrastructure failures caused by environmental contamination (shell env vars, config drift, etc.), explain how the fix prevents the same failure mode from recurring — the user wants assurance the root cause is permanently addressed, not just patched. Confidence: 0.70
- When debugging "Cannot access 'X' before initialization" TDZ errors in a Vite/Rollup production build, build with `--minify false` to reveal actual variable names instead of minified single-letter names (S,N,etc.) - this immediately identifies whether the error is in your code or a dependency. Confidence: 0.85
- When error-handling logic that branches on third-party SDK error properties silently never fires (e.g., fallback triggers, retry logic), inspect the SDK's actual error class in `node_modules` to confirm which properties exist — don't assume `err.status` works just because HTTP errors typically have it. SDKs vary: some use `statusCode`, some use `status`, some wrap in `err.response.status`. Checking the wrong property makes the branch unreachable and the fallback dead code. Confidence: 0.70
- When a third-party API returns HTTP 200 + success payload (messageId, etc.) but the expected side-effect doesn't occur (email never arrives, file not created, etc.), the API acceptance is NOT proof of delivery — check the provider's admin dashboard for silently-enforced prerequisites like sender verification, domain authentication, or webhook approvals. Some providers silently accept and drop requests for unverified identities rather than rejecting with an error code. Confidence: 0.70
- When a third-party library isn't behaving as configured (wrong CDN URL, unexpected defaults, ignored settings), verify that the configuration mechanism is actually consumed by the library — grep through `node_modules` source to confirm the library reads the env var / define / config key being set. Dead config (values set but never read by the library) creates false confidence and hides the real issue: the library is using its own hardcoded defaults. Replace dead config with the library's actual documented configuration API (e.g., `loader.config()` for `@monaco-editor/react`). Confidence: 0.75
- When patching a library in `node_modules` and the fix doesn't take effect after rebuild, grep ALL build artifacts of that library (ES module, UMD/CommonJS, minified and unminified variants) for the value being changed — bundlers like Vite may resolve to a different build target than the one you patched. A patch applied only to `lib/es/` is worthless if the bundler actually pulls from `lib/umd/`. Check every output format the library ships. Confidence: 0.80
- When a frontend metric always shows a placeholder/default (e.g., "Your Progress 0/8 solved" never changes), suspect the backend never computes or returns that field — read the backend service that builds the API response to confirm the field is absent before touching frontend code. A metric stuck at its default usually means the value was never populated server-side, and the correct fix is often to compute it in the backend (then rebuild + restart the Docker container), not to tweak the frontend display. Confidence: 0.70
- After deploying a fix (especially frontend changes served from a Docker container), verify the fix actually reached the running container — `docker exec` into the container and grep the built JS/CSS for the expected change before telling the user the fix is deployed. A build that succeeds locally and gets copied to `dist_nginx/` on the host means nothing if the container's own `dist/` was built from fresh `npm ci` inside the Dockerfile. The user saying "still not working" after multiple fix attempts usually means the fix never actually reached the deployed environment. Confidence: 0.85
- When the user believes stored DB content was changed from its original wording (e.g., problem statements rewritten from a story style to a direct style), investigate data provenance and recovery options before concluding: compare `createdAt` vs `updatedAt` per row (a bulk same-timestamp edit across all rows signals a rewrite), look for audit/history tables, and search git history plus seed/dump/backup files for the original text. When the user insists the system itself rewrote the data ("check properly it is being rewritten"), also exhaustively audit every code write path to the table — grep all create/update/upsert calls in both server and client, trace admin form save flows, JSON-import/sanitize features, and any auto-generation/autofill — and state definitively which single path (or the absence of any) explains the change. Confidence: 0.70
- When the user reports new code is "not deployed" in the running container, prove it before redeploying: compare the running container's image ID (`docker ps`) against the freshly built image ID, and `docker exec` into the container to grep for new-code markers (new service files, new function names) and check for the expected env vars. A stale image ID plus missing markers confirms the container runs old code — then recreate it with `docker compose up -d` and re-verify live. The user's "check it fix it" demands this evidence-based diagnosis, not an assumption that a successful build already deployed. Confidence: 0.75
- When a streaming feature (SSE/NDJSON chat) shows no visible streaming or no answer in production — the UI appears stuck (frozen logo/spinner, no text appearing) — check the reverse proxy configuration in addition to the backend and frontend bundles. An nginx proxy missing `proxy_http_version 1.1` (defaults to HTTP/1.0, which breaks chunked streaming), `proxy_buffering off`, and `X-Accel-Buffering off` will buffer or corrupt the stream, and browsers on HTTP/2 then fail with `ERR_HTTP2_PROTOCOL_ERROR` while the user just sees "streaming not seen". The fix in the proxy's location block: `proxy_http_version 1.1; proxy_buffering off; proxy_set_header X-Accel-Buffering off;` plus a raised `proxy_read_timeout` for long generations. The user reported exactly this symptom ("nexi logo is fixed, not answer, streaming not seen") after a successful container deploy — the code and backend were fine; the host nginx proxy was breaking the stream. Confidence: 0.80
