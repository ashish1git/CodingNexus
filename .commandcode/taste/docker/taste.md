# docker
- Docker setups must work cross-platform — Docker Desktop on Windows/macOS in addition to Linux. Avoid Linux-only features like `network_mode: host` in the primary compose file; when production needs host networking, provide a separate platform-agnostic dev compose file using standard bridge networking for local development. The user runs Docker Desktop, not a Linux server, on their laptop. Confidence: 0.75
- When a Docker container has correct HostConfig.PortBindings but empty NetworkSettings.Ports (corrupted port binding, often from "address already in use" during startup), "docker restart" is insufficient — stop, rm, and recreate the container via "docker compose up -d" to fix. Confidence: 0.85
- When `docker compose up -d --build` doesn't pick up .env changes (especially VITE_* or other build-time ARGs), use `docker compose build --no-cache` — Docker layer caching silently preserves old ARG values baked into cached layers, so a standard `--build` reuses stale layers and env changes never reach the bundled output. Confidence: 0.75
- Shell environment variables silently override `.env` file values for Docker Compose variable interpolation — if a variable like `JUDGE0_URL` is exported in the shell, `docker compose` uses the shell value instead of the `.env` file. When docker-compose resolves unexpected values despite the `.env` file being correct, check `env | grep VAR` to detect shell pollution. The defense is NOT to hardcode secrets into docker-compose.yml — that's a bad practice. Instead, keep runtime secrets exclusively in `.env.docker` (loaded via `env_file:`) and never reference secret `${VAR}` in the `environment:` block; only non-secret build args with safe defaults belong in `environment:` with `${VAR:-default}` interpolation. Confidence: 0.90
- Use a three-file env architecture that's industry standard and self-documenting for future developers: `.env.example` (template with `<CHANGE_ME>` placeholders, committed to git), `.env` (build-time ARGs only, no secrets, committed), `.env.docker` (runtime secrets loaded via `env_file:`, gitignored, the single source of truth). Each file has a clear, documented purpose. Confidence: 0.90
- Docker config files (docker-compose.yml, Dockerfile, .env.example) should include header comments explaining the env variable flow, what each file does, and setup instructions — the user wants future developers to understand the architecture just by reading the files, without needing tribal knowledge. Confidence: 0.90
- VITE_* environment variables are **build-time only** — `import.meta.env.VITE_*` is replaced with literal values by Vite during `vite build`. Setting `VITE_MAINTENANCE_MODE=true` as a runtime env var (via `env_file:` or `environment:`) has zero effect on frontend behavior because the JS bundle was already compiled with the old value. VITE_* vars must be declared as Dockerfile `ARG` + `ENV` in the build stage, and passed via `build-args` in docker-compose.yml. Runtime-only env vars only affect server-side `process.env.*` reads. Confidence: 0.85
- When a fix requires modifying a third-party library's behavior (hardcoded URLs, default config, etc.), use a **build-time transform** (Vite plugin `transform` hook, webpack loader, `patch-package`, etc.) rather than in-place `node_modules` file edits — `npm ci` inside the Docker build reinstalls fresh packages from the lockfile and reverts all manual patches. A Vite plugin runs during `vite build` regardless of what `npm ci` installed. Patching `node_modules` directly is a trap in Docker-based projects. Confidence: 0.85
- For this project, the backend is bundled inside the Docker image (the Dockerfile's builder stage runs `npm run build` and ships the server as plain Node), so a backend deploy is `docker compose build app` + `docker compose up -d --no-deps app` to recreate the container — not a separate backend build step on the host. Before building, inspect docker-compose files and current Docker state to confirm the right service name and image tags. Confidence: 0.70
